## 역할

현재 Git 변경사항을 확인해 실제 변경 내용에 맞는 커밋 메시지를 작성한다.

사용자가 명확히 요청한 경우에만 커밋 명령 예시를 제공하거나 `git commit` 실행을 돕는다.

## 핵심 원칙

- 실제 변경사항에 근거해서만 커밋 메시지를 작성한다.
- 구현되지 않은 내용, 의도만 있고 코드에 없는 내용, 추측은 커밋 메시지에 넣지 않는다.
- 하나의 커밋에 여러 성격의 변경이 섞여 있으면 커밋 분리를 제안한다.
- 확인하지 않은 테스트 실행 결과를 커밋 메시지나 설명에 포함하지 않는다.
- 커밋 실행 요청이 명확하지 않으면 메시지 초안만 제공한다.
- 커밋 메시지 접두사는 반드시 영어 소문자로 작성한다. 예: `feat`, `fix`, `docs`
- 접두사 뒤 요약 내용은 한국어로 작성한다.

## 작업 전 확인

커밋 메시지를 바로 작성하지 말고 먼저 변경 범위를 확인한다.

```shell
git status --short
git diff --stat
git diff --name-only
git diff --cached --stat
git diff --cached --name-only
```

staged 변경사항이 있으면 staged 기준으로 커밋 메시지를 작성한다.

staged 변경사항이 없고 unstaged 변경사항만 있으면 unstaged 변경사항 기준으로 메시지를 제안하되, 아직 stage되지 않았다고 안내한다.

파일 목록과 통계만으로 변경 내용을 파악하기 어렵다면 아래처럼 파일 단위로 좁혀서 확인한다.

```shell
git diff -- <file>
git diff --cached -- <file>
```

전체 diff를 무작정 읽지 않는다.

## 문서 로딩 규칙

커밋 메시지 작성에는 기본적으로 프로젝트 문서를 읽지 않는다.

다만 변경사항의 의미를 파악하기 위해 필요할 때만 아래 문서를 읽는다.

- `README.md`
    - 실행 방법, 환경변수, 프로젝트 범위 변경이 커밋 내용과 직접 관련될 때
- `docs/api/{domain}.md`
    - API 문서 변경 또는 Controller/DTO 변경의 의미를 확인해야 할 때
- `docs/ERD.md`
    - Entity, Repository, DB schema 변경의 의미를 확인해야 할 때
- `docs/CODE_CONVENTION.md`
    - 커밋 메시지 컨벤션이 문서에 명시되어 있는지 확인해야 할 때
    - 이 파일은 인덱스로만 사용하고 필요한 문서만 개별적으로 읽는다.

`docs/**/*.md`, `docs/api/*.md` 전체를 한 번에 읽지 않는다.

## 작업 모드

### 1. 커밋 메시지 제안 모드

사용자가 "커밋 메시지 작성해줘", "커밋 문구 추천해줘"처럼 메시지만 요청하면 사용한다.

1. staged 변경사항이 있는지 확인한다.
2. staged 변경사항이 있으면 staged 기준으로 메시지를 작성한다.
3. staged 변경사항이 없으면 unstaged 기준으로 메시지를 제안하고 stage 필요 여부를 안내한다.
4. 변경 성격에 맞는 타입을 선택한다.
5. 제목 1개와 필요하면 본문 bullet을 함께 제안한다.

### 2. 커밋 분리 제안 모드

변경사항에 서로 다른 목적이 섞여 있으면 사용한다.

1. 변경 파일을 성격별로 나눈다.
2. 커밋을 몇 개로 나누면 좋을지 제안한다.
3. 각 커밋별 메시지 후보를 작성한다.
4. 사용자가 원하면 stage 단위 분리 방법을 안내한다.

### 3. 커밋 실행 보조 모드

사용자가 "이 메시지로 커밋해줘", "커밋까지 해줘"처럼 명확히 요청하면 사용한다.

1. staged 변경사항이 있는지 확인한다.
2. staged 변경사항이 없으면 먼저 stage가 필요하다고 안내한다.
3. 메시지를 다시 확인한 뒤 `git commit -m "<message>"` 실행을 돕는다.
4. 커밋 후 커밋 해시와 제목을 확인해 알려준다.

## 커밋 메시지 형식

기본 형식은 아래처럼 작성한다.

```text
type: 변경 내용을 짧게 요약
```

타입은 변경의 핵심 성격에 맞춰 하나만 고른다.

- `feat`: 기능 추가
- `fix`: 버그 수정
- `refactor`: 구조 개선, 동작 변화 없는 리팩토링
- `docs`: 문서 수정
- `test`: 테스트 추가 또는 수정
- `chore`: 설정, 빌드, 의존성, 기타 유지보수

예시:

```text
docs: 트러블슈팅 작성 스킬 추가
test: 로그인 실패 케이스 검증 추가
fix: 주문 취소 시 재고 복구 누락 수정
```

본문이 필요하면 제목 아래에 변경 이유와 주요 변경사항을 짧게 적는다.

```text
feat: 결제 웹훅 멱등성 처리 추가

- 웹훅 이벤트 ID 중복 여부를 저장하도록 추가
- 동일 이벤트가 재전송되면 결제 상태를 중복 변경하지 않도록 처리
```

## 결과 형식

기본 응답은 아래 형식으로 작성한다.

````markdown
추천 커밋 메시지:

```text
docs: 트러블슈팅 작성 스킬 추가
```

근거:
- `.agents/skills/troubleshooting-writer/SKILL.md` 추가
- 트러블슈팅 문서 작성 절차와 템플릿 정의
````

변경이 여러 개로 섞여 있으면 아래 형식으로 작성한다.

````markdown
커밋을 나누는 편이 좋겠습니다.

1. `docs: 스킬 문서 양식 정리`
   - 기존 PR, 리뷰, 테스트 스킬 구조 정리

2. `docs: 트러블슈팅 작성 스킬 추가`
   - 새 트러블슈팅 스킬 추가
````

## 금지사항

- 변경사항을 확인하지 않고 커밋 메시지를 작성하지 않는다.
- staged 변경사항과 unstaged 변경사항을 구분하지 않고 섞어서 말하지 않는다.
- 실제 변경과 맞지 않는 타입을 붙이지 않는다.
- 커밋 메시지 접두사를 대문자나 한국어로 작성하지 않는다.
- 커밋 메시지 요약 내용을 영어로 작성하지 않는다.
- 확인하지 않은 테스트 통과 여부를 포함하지 않는다.
- 사용자가 커밋 실행을 요청하지 않았는데 `git commit`을 실행하지 않는다.
- 커밋 메시지 작성을 위해 프로젝트 문서 전체를 예방 차원에서 읽지 않는다.
