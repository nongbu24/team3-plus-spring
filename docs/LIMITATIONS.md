# 도메인별 기능 한계와 추후 해결할 문제

이 문서는 현재 구현된 API 문서와 주요 서비스 흐름을 기준으로, 각 도메인에서 아직 남아 있는 기능적 한계와 추후 개선 과제를 정리한다.

## 1. 인증 도메인

### 현재 기능

- 회원가입
- 로그인 및 JWT access token 발급
- 로그아웃

### 기능별 한계

| 기능 | 현재 한계 | 추후 해결할 문제 |
| --- | --- | --- |
| 회원가입 | 이메일 중복과 비밀번호 암호화는 처리하지만, 이메일 인증이나 휴대폰 인증 같은 실사용자 검증 절차는 없다. | 가입자가 실제 소유한 이메일/전화번호인지 검증하는 인증 절차를 추가해야 한다. |
| 로그인 | access token만 발급하는 구조라 장시간 로그인 유지와 안전한 재발급 흐름이 제한적이다. | refresh token을 도입하고, 토큰 재발급/만료/탈취 대응 정책을 설계해야 한다. |
| 로그아웃 | 로그아웃된 access token을 서버에서 차단할지, 클라이언트 폐기 방식으로만 처리할지 운영 정책이 명확히 고정되어 있지 않다. | 로그아웃 토큰 무효화 방식(블랙리스트 등)을 도입할지 정책을 확정해야 한다. |
| 보안 정책 | 로그인 실패 횟수 제한, 계정 잠금, 비밀번호 변경 기능이 없다. | 무차별 대입 공격 방지를 위한 로그인 제한과 비밀번호 재설정/변경 기능을 추가해야 한다. |

## 2. 회원 도메인

### 현재 기능

- 내 정보 조회
- 회원 탈퇴

### 기능별 한계

| 기능 | 현재 한계 | 추후 해결할 문제 |
| --- | --- | --- |
| 내 정보 조회 | 조회 기능만 있고 이름, 전화번호, 비밀번호 수정 기능은 없다. | 회원 정보 수정 API와 수정 가능 필드의 검증 정책을 추가해야 한다. |
| 회원 탈퇴 | soft delete 방식으로 탈퇴 처리하지만, 탈퇴 후 주문/결제/채팅 데이터 보존 정책이 세분화되어 있지 않다. | 탈퇴 회원의 개인정보 마스킹, 주문 이력 보존, CS 기록 보관 기간을 도메인별로 분리해야 한다. |
| 이메일 재사용 제한 | 탈퇴한 이메일도 재가입할 수 없도록 막고 있다. | 서비스 정책에 따라 영구 제한이 맞는지, 일정 기간 후 재가입을 허용할지 결정해야 한다. |
| 관리자 기능 | 일반 회원 관점 API만 있고 관리자용 회원 조회/권한 변경 기능은 없다. | 운영자가 회원 상태를 확인하고 권한을 관리할 수 있는 관리자 API가 필요하다. |

## 3. 상품 도메인

### 현재 기능

- 상품 목록 조회
- 상품 상세 조회
- 인기 상품 조회
- 챗봇용 상품 검색

### 기능별 한계

| 기능 | 현재 한계 | 추후 해결할 문제 |
| --- | --- | --- |
| 상품 목록 조회 | 기본 필터와 정렬은 가능하지만, 가격 범위, 재고 여부, 복합 검색 조건은 부족하다. | 실제 쇼핑몰 탐색에 필요한 가격대, 브랜드, 품절 제외, 다중 카테고리 필터를 확장해야 한다. |
| 상품 상세 조회 | 상세 조회 시 조회수를 증가시키지만, 같은 사용자의 반복 조회나 봇 트래픽을 구분하지 않는다. | 인기 상품 신뢰도를 높이기 위해 중복 조회 방지, 기간별 조회수 집계, 비정상 트래픽 필터링이 필요하다. |
| 인기 상품 조회 | 단순 조회수 기준이라 구매 전환율이나 최근성은 반영하지 않는다. | 조회수, 주문 수, 장바구니 추가 수, 최근 기간 가중치를 조합한 인기 상품 산정 방식이 필요하다. |
| 상품 관리 | 사용자 조회 API 중심이며 상품 등록, 수정, 삭제, 재고 조정 API가 없다. | 관리자용 상품 CRUD와 재고 변경 이력 관리 기능을 추가해야 한다. |
| 상품 검색 캐싱 | 최초 기획 단계에서는 상품 검색에 Local Cache v1/v2를 분리 적용할 계획이었지만, 실제로는 상품 검색에는 캐시가 적용되지 않았고 쿠폰 이벤트 목록 조회(`GET /api/coupon-events`)에 Redis 캐시가 적용됐다. | 상품 검색에도 캐시가 필요하다면 별도로 설계하거나, 계획이 바뀐 배경을 문서에 명시해야 한다. |
| 상품 조회 인덱스 | 최신순(`created_at`) 정렬 기준으로만 인덱스를 분석했다. 가격순(`PRICE_ASC`/`PRICE_DESC`) 정렬은 별도 인덱스 최적화가 되어 있지 않다. | 가격순 정렬 쿼리를 대상으로 별도 인덱스 분석을 진행해야 한다. ([docs/index-performance.md](index-performance.md)) |
| 인기 검색어 | Redis ZSet 기반 인기 검색어 기능은 ERD 설계 단계에서 `search_keywords` 테이블까지는 정의했지만 구현되지 않았다. 현재는 조회수 기준 인기 상품 조회로만 제공한다. | 검색 횟수 집계와 랭킹 API를 별도로 구현해야 한다. |

### 현재 기능

- 쿠폰 이벤트 등록
- 발급 중인 쿠폰 이벤트 목록 조회 (Redis 캐시 적용)
- 선착순 쿠폰 발급
- 내 사용 가능 쿠폰 조회
- 주문 생성 시 쿠폰 사용

### 기능별 한계

| 기능 | 현재 한계 | 추후 해결할 문제 |
| --- | --- | --- |
| 쿠폰 이벤트 등록 | 관리자 등록은 가능하지만 수정, 조기 종료, 재오픈 기능이 없다. | 운영 중 잘못 등록된 이벤트를 수정하거나 종료할 수 있는 관리 기능이 필요하다. |
| 쿠폰 발급 | Redis 원자적 카운터로 선착순 재고를 1차 제어하고 DB 조건부 UPDATE로 2차 검증하지만, 통과 이후의 DB 반영은 여전히 요청과 동기적으로 처리된다. | 트래픽이 커지면 성공 요청만 큐에 적재하고 DB 반영은 비동기 워커가 처리하도록 분리하는 구조를 검토해야 한다. |
| 쿠폰 목록 조회 | 사용 가능한 쿠폰만 조회하고, 사용 완료/만료 쿠폰 이력 조회는 없다. | 사용자가 쿠폰 사용 내역과 만료 내역을 확인할 수 있는 이력 조회가 필요하다. |
| 쿠폰 사용 | 주문 전체 금액 기준 할인만 고려되며 상품별 적용 조건은 없다. | 특정 카테고리/상품 전용 쿠폰, 최소 주문 금액, 최대 할인 금액 같은 정책을 확장해야 한다. |
| 쿠폰 만료 | 조회 시점에 만료 여부를 판단하지만, 만료 상태를 일괄 변경하는 배치가 명확하지 않다. | 만료 쿠폰 상태를 주기적으로 정리하는 스케줄러 또는 배치 작업이 필요하다. |

### 동시성 제어 회고

선착순 쿠폰 발급의 동시성 제어는 비관적 락 → 분산 락(Lettuce 기반 스핀 락) → 분산 락(Redisson 기반 공정 락) → Redis 원자적 `DECR` 카운터 순서로 방식을 바꿔가며 구현했다. "동시성을 막는다"는 같은 목표 아래에도 보호 범위, 대기 방식, 순서 보장 여부가 도구마다 전혀 다르다는 것을 직접 부딪혀가며 배웠고, "분산 락을 적용했다"는 결과보다 "왜 이 방식을 선택했고 무엇을 포기했는지"를 설명할 수 있어야 한다는 피드백이 가장 크게 남았다.

다만 지금 구조도 한계가 없는 것은 아니다. Redis `DECR`로 재고 차감 자체는 원자적으로 처리되지만, 그 다음 DB의 `issuedQuantity` 증가와 `UserCoupon` 저장은 여전히 요청과 동기적으로 처리된다. 트래픽이 지금보다 훨씬 커져 순간적으로 재고를 통과한 요청이 몰리면 같은 쿠폰 이벤트 row에 DB 경합이 발생할 수 있다. 다음 대용량 트래픽 처리 프로젝트에서 기회가 된다면, 성공한 요청만 큐에 적재하고 DB 반영은 비동기 워커가 처리하도록 분리하는 방식을 직접 설계해보고 싶다.

## 8. 결제/PortOne 도메인

### 현재 기능

- PortOne 공개 설정 조회
- 결제 시작
- 무료 결제 완료
- 진행 중 결제 중단
- 결제 승인 검증
- PortOne 연동용 포트 구조

### 기능별 한계

| 기능 | 현재 한계 | 추후 해결할 문제 |
| --- | --- | --- |
| 결제 시작 | 결제 대기 상태 전환은 가능하지만, 결제창 이탈이나 장시간 미완료 주문을 자동 정리하는 정책은 제한적이다. | 결제 대기 만료 시간과 자동 취소 스케줄러를 도입해야 한다. |
| 무료 결제 | 컨트롤러에는 `/free-complete`가 있지만 결제 API 문서(`docs/api/payments.md`)에는 반영되어 있지 않다. | 무료 결제 조건, 허용 금액을 정리해 API 문서에 반영해야 한다. |
| 결제 승인 검증 | PortOne 조회와 금액 검증은 하지만, 취소 결과가 불명확하면 수동 확인 상태가 필요하다. | `REVIEW_REQUIRED` 상태를 운영자가 확인하고 재처리할 수 있는 관리자 기능이 필요하다. |
| 결제 상태 동기화 | 결제 상태 동기화가 사용자의 결제 확정 요청(`/api/payments/confirm`)에만 의존한다. 웹훅 연동은 아직 구현하지 않아, 브라우저 종료나 네트워크 오류로 confirm 요청이 도달하지 못하면 상태가 자동으로 갱신되지 않는다. | PortOne 웹훅을 연동해 서버 쪽에서도 결제 상태를 감지하고, 장시간 미완료된 주문/결제를 스케줄러로 재확인·복구하도록 개선해야 한다. |
| PG 장애 대응 | 외부 API 실패 시 예외 처리 중심이며 재시도/보상 작업 정책이 부족하다. | 결제 조회/취소 재시도, 실패 이벤트 기록, 운영자 알림 체계를 추가해야 한다. |

### 결제 상태 동기화 회고

현재 결제 상태 동기화는 사용자의 결제 확정 요청(`/api/payments/confirm`)에만 의존한다. PortOne 웹훅 수신은 아직 구현하지 않아서, 브라우저 종료나 네트워크 오류로 confirm 요청이 서버에 도달하지 못하면 주문과 결제가 `READY`, `PAYMENT_PENDING`, `CANCEL_REQUESTED` 등의 상태로 남아도 이를 감지·복구할 방법이 없다. 이 경우 재고와 쿠폰이 계속 선점될 수 있다. 추후 PortOne 웹훅을 연동해 결제 상태를 서버 쪽에서도 감지하고, 장시간 처리되지 않은 주문과 결제를 스케줄러로 주기적으로 재확인·복구하도록 개선할 예정이다.

## 우선순위 제안

| 우선순위 | 해결 과제 | 이유 |
